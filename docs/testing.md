# План тестирования FitHome

> Статус: Этап 1 — план. Инфраструктура Vitest уже настроена в обоих пакетах (`backend/vitest.config.ts`, `frontend/vitest.config.ts`) и покрыта smoke-тестами; сами тесты функциональности пишутся по мере реализации этапов.

## 1. Инструменты

| Область | Инструмент | Конфигурация |
|---|---|---|
| Backend unit-тесты | Vitest | `backend/vitest.config.ts` |
| Frontend unit-тесты | Vitest | `frontend/vitest.config.ts` |
| Тестирование React-компонентов | Vitest + `@testing-library/react` + `jsdom` | подключается на этапе 2 |
| Тестирование HTTP | Vitest + `supertest` (тестирование `app.ts` без запуска порта) | подключается на этапе 2 |
| Мок-данные БД | `vitest-mock-extended` для Prisma Client | подключается на этапе 2 |

Никаких других тест-раннеров и e2e-инструментов на текущем этапе не устанавливается (e2e — см. §6).

## 2. Принципы

1. **Тест следует за реализацией.** Каждый этап ([architecture.md §9](architecture.md#9-план-развития-этапы-2)) заканчивается покрытием написанного кода тестами — коммит без тестов новой логики не принимается.
2. **Тестируем публичное поведение.** Services тестируются через их интерфейс, а не через внутренние вызовы; контроллеры — через HTTP (supertest на `app`).
3. **Быстрый контур.** Полный прогон unit-тестов — до 30 секунд; интеграционные тесты БД запускаются отдельно (см. §5).
4. **Дeterminism.** Время — через инъекцию/моки, никакой зависимости от реальных часов и сети.

## 3. Backend — что и как тестируем

### 3.1. Уровни

| Уровень | Что проверяем | Подход |
|---|---|---|
| **Services** (приоритет 1) | Бизнес-логика: права доступа (`userId`), правила метрик упражнений, подсчёт статистики, регистрация (User + UserSettings в одной операции) | Мок `repositories`; чистые функции без HTTP |
| **Controllers/routes** (приоритет 2) | Контракты [api.md](api.md): статус-коды, формат ошибок `VALIDATION_ERROR`/`NOT_FOUND`/…, пагинация | supertest на `app` (создан в `app.ts` без прослушивания порта — это уже учтено в архитектуре) |
| **Repositories** (приоритет 3) | Корректность запросов Prisma, каскады из [database.md §3](database.md#3-правила-целостности) | Интеграционные тесты на реальной SQLite (`DATABASE_URL` указывает на временный файл, миграции применяются перед прогоном) |
| **Middlewares** (приоритет 2) | `auth`: 401 без токена/с просроченным; `error-handler`: единый формат ошибок | unit-тесты + проверка через supertest |

### 3.2. Структура тестов

```
backend/src/**/__tests__/
  *.test.ts        # тесты лежат рядом с тестируемым модулем
```

Соглашение имён: `<модуль>.test.ts` (например, `auth.service.test.ts`, `health.routes.test.ts`).

### 3.3. Ключевые сценарии (по этапам)

**Этап 2 — авторизация:**
- регистрация создаёт пользователя и настройки; дубликат email → 409;
- вход с верными/неверными данными (сообщение не раскрывает, что неверно);
- refresh-ротация: старый refresh-токен отклоняется после использования;
- доступ к защищённым эндпоинтам без/с/с просроченным токеном.

**Этап 3 — упражнения и программы:**
- пользователь видит общие упражнения + только свои персональные;
- чужую программу нельзя прочитать/изменить → 403;
- `order` программы: дубликат → 400;
- цели ProgramExercise проверяются по метрике упражнения;
- soft delete программы (`isActive=false`).

**Этап 4 — тренировки и статистика:**
- `POST /api/workouts` сохраняет тренировку и результаты одной транзакцией; при ошибке в результатах ничего не сохраняется;
- подсчёт сводки статистики (по фиксированному набору мок-данных);
- пагинация: `page`, `limit`, `total`.

**Этап 5 — настройки:**
- значения по умолчанию при регистрации;
- обновление только переданных полей;
- отклонение недопустимых значений `unit`/`theme`.

## 4. Frontend — что и как тестируем

| Что | Примеры | Инструмент |
|---|---|---|
| Утилиты и сервисы | HTTP-клиент: подстановка Bearer-токена, повтор запроса после refresh, разбор ошибок | Vitest + мок `fetch` |
| Хуки | загрузка данных: loading/error/success состояния | Vitest + `@testing-library/react` |
| Компоненты | `Button`, `TextField` (ошибки валидации), `EmptyState` | Vitest + Testing Library + jsdom |
| Страницы-потоки | регистрация: отправка формы, показ ошибки сервера | Testing Library, мок `api/` |
| Context | auth-контекст: вход/выход/восстановление сессии | Testing Library |

Структура: тесты рядом с кодом — `frontend/src/**/__tests__/*.test.ts(x)`.

Приоритеты: (1) HTTP-клиент и auth-сервисы, (2) формы авторизации, (3) ключевые компоненты, (4) остальное по мере реализации.

## 5. Организация прогонов

```bash
# Разработка (watch-режим)
npm test -- --watch        # в backend/ или frontend/

# Одноразовый прогон + покрытие
npm run test:coverage      # coverage в .coverage/ (в .gitignore)

# CI (добавляется на этапе 2)
# 1) lint/typecheck  2) backend tests (unit)  3) backend integration (SQLite tmp)  4) frontend tests
```

Порог покрытия: **≥ 80% statements** для `services/` и `src/api` frontend; для контроллеров — по критическим контрактам ошибок. Coverage-отчёт — `coverage/` (исключён в `.gitignore`).

## 6. Тестирование вне Vitest

| Вид | Инструмент | Когда |
|---|---|---|
| Ручной smoke-чек | чек-лист из [design.md §6](design.md#6-ux-потоки) на 360 px и десктопе | конец каждого этапа |
| Доступность | проверка контраста и клавиатурной навигации ([design.md §7](design.md#7-доступность)) | этап 2 и далее |
| e2e | Playwright (отдельное решение на этапе 4+) | после стабилизации потоков |
| Проверка перехода на PostgreSQL | прогон интеграционных тестов repositories с `DATABASE_URL` PostgreSQL | этап 6 ([database.md §8](database.md#8-стратегия-перехода-sqlite--postgresql)) |
